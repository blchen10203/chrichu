# Reachdle Screens Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The first playable release: Daily and Infinite modes with the silhouette and bar rounds, results, sharing, the home and help pages, deployed to Vercel.

**Architecture:** Thin React client components over the engine from plan 2. Components hold only view state; every rule (scoring, snapping, round picking, saving) is an engine call. Pages are static HTML that read the date and `localStorage` only after mounting in the browser.

**Tech Stack:** Next.js 16 (App Router, static export), React 19, Tailwind 4, Playwright for end-to-end tests.

**Spec:** `docs/superpowers/specs/2026-11-10-reachdle-design.md` (sections 7.1, 7.2, 8, 10, 12, 14).
**Mockups:** `docs/superpowers/mockups/` holds four phone-sized HTML mockups with inline styles: `Main.dc.html` (reach round), `BarRound.dc.html` (bar round), `Reveal.dc.html`, `Results.dc.html`. Read the markup inside `<x-dc>` as the visual spec: sizes, spacing, colours, copy. Ignore the `support.js` wrapper and the script block.

This is plan 3 of 4. It needs plan 2 (engine) finished first. Plan 4 is Survival and the weekly Action.

## Global Constraints

- Work in `web/`. Run commands from `web/`. Commit directly to `main`.
- **Read before coding:** `web/AGENTS.md` says this Next.js differs from what you know. Before the first Next.js change in each task, read the relevant guide under `web/node_modules/next/dist/docs/01-app/` (static exports, fonts, client components; `02-guides/testing/playwright.md` for Task 2).
- Static export: no server code, no `next/image` optimisation (use plain `<img>`), no route handlers, no cookies.
- Never read the date, `localStorage` or `Math.random()` during render. Read them in an effect after mount, and render a neutral placeholder until then, so server HTML and first client render match.
- No game rule is written in a component. Use these engine functions (plan 2):

  - `@/lib/images`: `fighterImage(id, hasImage)`; `@/lib/config`: `config`
- Spec rules, verbatim: the reference fighter is always blue and the player's estimate is always red; controls are real buttons and sliders; the drag handle is keyboard operable and arrow keys move one snap; one Daily attempt per day; each Lock In is saved immediately.

- Colours (from the mockups): background `#0F1115`, panel `#181B22`, line `#2A2E38`, tick `#4A5060`, text `#F2F3F5`, muted `#A0A6B2`, blue `#5B9BFF`, red `#FF5A5F`, action button `#D92D35`. - [ ] **Step 3: Implement the Daily page** (spec 7.1)

A client component. Everything below happens after mount; before it, render only the header row.

1. `today = localDate(new Date())`, fixed for the life of the page. `state = load(browserStorage())`.
2. If `state.daily.days[today]` is missing: `startDay(state, today, dailySet(today, fighters, metrics))` and save.
   Otherwise: `repairRounds(day.rounds, day.guesses.length, today, fighters, metrics)`; if that changed the rounds, store them on the day and save.
3. The current round index is `day.guesses.length`. Show `RoundShell` for it with mode label `DAILY · ROUND {i + 1} / 5`.
4. `top` is five pips and the running score, as in the mockup: a pip is white for a played round, red for the current one, and the line colour for rounds to come; then `Score {sum of scores so far}`.
